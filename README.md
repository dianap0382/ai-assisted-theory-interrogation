# AI-Assisted Theory Development

Companion repository to the research proposal *AI-Assisted Theory Development: Interrogating Theory Through Its Computational Representation*. It contains five case-level computational analyses demonstrating the proposed approach.

## Overview

Theory makes complex empirical phenomena intelligible by specifying constructs, the distinctions and relationships among them, and the mechanisms that account for those phenomena. This specification also shapes what researchers can see.

To search large bodies of text, theory must first be encoded in a computational representation: dictionaries, embeddings, similarity measures, and mapping rules. Applied at scale, this representation recognizes what resembles existing constructs and systematically overlooks what does not. When used only to classify evidence into existing constructs, computational methods reproduce existing theory more efficiently.

We develop an architecture in which **theory both structures the search and is what the search examines**. The computational representation detects where theory holds or breaks down; human adjudication distinguishes computational artifacts from theoretical opportunities.

## Four epistemic questions

The architecture is organized around four epistemic functions. Each function poses one question to theory:

1. **Recognition:** Does theory see the phenomenon?
2. **Differentiation:** Do its distinctions hold?
3. **Dynamics:** What happens to practices in enactment?
4. **Limits:** What remains persistently unexplained?

## From signal to theoretical elaboration

A signal is not a finding. The six-step cycle proceeds under human adjudication:

1. **Detect:** The computational representation detects a signal.
2. **Return to evidence:** Researchers examine the passages or interview segments that produced the signal.
3. **Representational sensitivity:** Researchers test whether the signal persists when dictionaries, models, or granularity are altered.
4. **Puzzle:** A surviving signal is stated as a theoretical puzzle using the question its epistemic function poses.
5. **Rival explanations:** Researchers assess whether existing theory already accounts for the pattern, whether it is a contextual variation of a known mechanism, or whether it points to something theory omits.
6. **Elaboration:** If rival explanations do not account for the pattern, researchers determine whether to redraw a construct boundary, specify a configuration of mechanisms, add a contingency or process of change, or state the limits of theory’s scope.

Returning to the evidence can itself dissolve a signal. The cycle is designed to record the signal, evidence, checks, rival explanations considered, and decision taken, making human adjudication auditable rather than tacit. Theoretical elaboration can then revise the computational representation so that the search begins again.

AI does not develop theory. It expands systematic, human-directed search for theoretical opportunities, while explanation and inference remain with researchers.

## Repository scope

The repository demonstrates the architecture through five candidate cases in corporate venturing, drawing on organizational design theory, corporate venturing scholarship, and practitioner interviews.

**The repository supports:**
- Reproduction of specified case-level computational analyses.
- Verification of selected indicators.
- Inspection of available supporting analytical records.

**It does not support:**
- Reconstruction of the original literature and interview corpora.
- Independent reproduction of researcher adjudication or theoretical interpretations.

## Getting started

Use **Python 3.11 or later** (core scripts checked with Python 3.13.5). Create a virtual environment and install the dependencies listed in requirements.txt.

From the repository root, execute the following commands. The scripts access their inputs and save generated results within their respective case directories.

```bash
python -m venv .venv

# Windows: 
.venv\Scripts\activate

# macOS/Linux: 
source .venv/bin/activate

python -m pip install -r requirements.txt

# Core case-level analyses
python case1/scripts/run_case1.py
python case2/scripts/run_case2.py
python case3/scripts/run_case3.py
python case4/scripts/verify_case4.py
python case5/scripts/verify_case5.py

# Optional semantic embedding analyses
python case1/scripts/run_semantic_case1.py
python case3/scripts/run_semantic_case3.py
```

The core lexical analyses and indicator checks do not require pretrained models. The optional semantic analyses download the specified sentence-transformer models on first use.

Generated results are saved in each case’s outputs/ directory. Some additional files in these directories document supporting analyses and researcher adjudication rather than outputs regenerated by the listed scripts. The case-specific verification instructions identify which results can be reproduced and how they should be compared with the saved outputs.

## Analytical architecture

The five cases draw on two complementary comparisons.

Comparison A: Corporate venturing scholarship and organizational design theory. Practices identified in corporate venturing research are mapped against organizational design constructs. Mapping patterns generate candidate signals of preservation, decomposition, recombination, and non-fit, allowing researchers to examine whether existing theoretical constructs recognize and adequately differentiate the practices described in the literature.

Comparison B: Practitioner enactment and ostensive baselines. Interview evidence is compared with literature-derived descriptions of organizational practices. Three diagnostic measures distinguish different relationships between established expectations and actual enactment: the Ostensive Invocation Rate (OIR-L and OIR-S) captures lexical and semantic invocation of the baseline; the Performative Improvisation Rate (PIR) captures departures from it; and the Tension Index (TI) captures the conjunction of invoking the baseline’s vocabulary while departing from it.

These comparisons produce signals for the four epistemic functions. The six-step theory interrogation cycle then determines whether a signal reflects a computational artifact, an observation already explained by existing theory, or an opportunity for theoretical elaboration. The accompanying technical documentation records the available analytical procedures, evidence, and researcher adjudication, while identifying limitations in what can be independently reproduced.

## Case guide

The five cases illustrate how computational representations can support four epistemic functions of theory interrogation: recognition, differentiation, dynamics, and limits. Each analysis generates or examines diagnostic signals that require interpretation against the underlying evidence.

- **Case 1: Incentives | Recognition (preservation).** Examines whether incentive-related practices in corporate venturing are recognized by existing organizational design constructs. Run `case1/scripts/run_case1.py` for TF-IDF comparisons of theoretical anchors and literature-derived passages. Optionally run `case1/scripts/run_semantic_case1.py` for sentence-embedding comparisons. The evidence does not yet establish a qualified preservation finding.
- **Case 2: Autonomy | Differentiation (decomposition).** Examines whether established theoretical categories adequately distinguish dimensions of corporate venturing unit autonomy. Run `case2/scripts/run_case2.py` for candidate provenance checks, dictionary sensitivity, and lexical comparisons. The decomposition signal remains sensitive to representational choices. The original full-corpus clustering is not reproduced.
- **Case 3: Partner integration | Differentiation (recombination).** Examines whether empirical practices suggest connections between theoretical constructs that are ordinarily treated separately. Run `case3/scripts/run_case3.py` for dictionary screening and candidate similarity analysis. Optionally run `case3/scripts/run_semantic_case3.py` for embedding comparisons. Recombination is supported descriptively within one article, but independent recurrence has not been established.
- **Case 4: Early-stage investment | Dynamics (tension).** Examines why a corporate venturing unit with formal authority over its investment-stage strategy nevertheless abandons early-stage investing. Run `case4/scripts/verify_case4.py` to verify saved pseudonymized indicators and case-level distinctions. This case illustrates the full six-step theory interrogation cycle. The resulting theoretical elaboration distinguishes formal decision authority from the organizational buffering required to sustain an early-stage investment strategy when the parent firm’s expectation horizon is misaligned with the investment stage.
- **Case 5: Fast-track governance | Limits (candidate non-fit).** Examines whether an apparent mismatch between established theory and empirical practice indicates a theoretical limit. Run `case5/scripts/verify_case5.py` to check saved indicators and threshold sensitivity. Returning to the evidence shows that the fast-track procedure was proposed rather than enacted, so the candidate non-fit does not survive qualitative adjudication.

The repository distinguishes three categories of evidence:

1. Regenerated computational results: Outputs produced by the supplied scripts that reviewers can compare with saved results.
2. Verified indicators: Existing data and analytical distinctions checked by verification scripts against specified criteria.
3. Supporting analytical records: Additional outputs, source-level assessments, and researcher adjudication that are documented but not independently regenerated.

Computational reproducibility does not, by itself, establish the validity of a theoretical interpretation. The theory interrogation cycle comprises six stages: Detect, Return to Evidence, Representational Sensitivity, Puzzle, Rival Explanations, and Elaboration. Computational signals initiate this process but do not replace returning to the underlying evidence or researcher adjudication.
